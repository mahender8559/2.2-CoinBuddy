1. Core accounting model
Rule
The app should treat money in two major buckets:

Assets: things you own
bank accounts, cash wallet, investments
Liabilities: things you owe
credit cards, loans, mortgages
The app should then calculate:

Total Assets
Total Liabilities
Net Worth = Total Assets - Total Liabilities
UI
The dashboard should show:

asset summary
liability summary
net worth
Tables
Accounts table stores account metadata
Transactions table stores every money movement
Calculation
The balance of an account is not stored manually as the only truth. It is calculated from the transaction ledger.

2. Single source of truth: ledger-first balance logic
Rule
A balance should never be edited blindly. Instead:

create or update an opening balance transaction
then recompute the account balance from the ledger
Why this matters
This prevents “ghost balances” where the UI shows a value that has no real transaction behind it.

UI
When a user edits an account’s opening balance in the account modal, the app should:

update the opening balance transaction
then recalculate the visible balance
Tables
transactions has fields like:
transaction_type
amount
from_account_id
to_account_id
is_opening_balance
is_verified
Calculation
The balance is derived by summing the effect of all verified transactions.

In the current project, this is reflected in balanceManager.ts and the view in sqliteSchema.ts.

3. Transaction types and sign rules
Rule
Every transaction should be classified as one of:

Income
Expense
Transfer
Opening Balance
UI
The add transaction form should let the user choose:

type
account
amount
category
Tables
transactions.transaction_type
transactions.amount
transactions.from_account_id
transactions.to_account_id
Calculation logic
The app uses direction-based logic:

Income increases an asset account
Expense decreases an asset account
Transfer moves value between accounts
For liability accounts, the direction is reversed in some cases
Example:

If you add income to a bank account, asset balance goes up
If you add expense from a bank account, asset balance goes down
If you pay a liability, it should reduce debt rather than be treated like ordinary spending
4. Opening balance rules for assets and liabilities
Rule
When a user creates or edits an account, the app should preserve data consistency by creating or updating an opening balance transaction.

UI
In the account creation/edit modal:

the user sees an “initial balance” or “starting balance”
the app should not just change the visible balance directly
Tables
accounts stores the account itself
transactions stores the opening balance entry
Calculation
The opening balance acts as the starting point for the account’s balance history.

For example:

account starts at 0
income of 5000 is recorded
later the initial balance is edited to 5900
the app should update the opening balance transaction, not invent a balance
This is exactly the kind of rule discussed in the PDF and implemented in AppContext.tsx.

5. Prevent invalid initial balance changes
Rule
If a user lowers the opening balance too much, it can make past transactions create an impossible balance (negative cash or overpaid debt).

UI
The app should show a warning such as:

“Cannot set initial balance lower than ₹X because existing transactions would make the account negative.”
Tables
This uses:

historical transactions
opening balance transaction
account type
Calculation
The app should calculate the lowest historical cumulative effect of all transactions and block edits that would break the account.

This is already reflected in the validation logic in AppContext.tsx.

6. Liability-specific rules: debt and credit limits
Rule
For liabilities like credit cards and loans, the logic is different from assets.

For liability accounts:

payments reduce debt
charges increase debt
the app must avoid creating a negative debt balance that contradicts history
if a credit limit exists, the initial debt should not exceed the limit after applying past history
UI
The app should:

show debt balances
show credit limit
warn if a new opening debt would conflict with prior transactions
Tables
accounts has fields like:
credit_limit
interest_rate
monthly_emi
interest_calculation_type
Calculation
For liabilities, the app checks:

minimum allowed starting debt
maximum allowed starting debt if a credit limit exists
7. Recurring transaction rules
Rule
For recurring payments, the date should usually be the scheduled recurring date, not the approval date.

UI
When a recurring payment is due:

pre-fill the date with the scheduled recurring date
allow the user to edit it if needed
Tables
transactions has:
is_recurring
is_verified
date
Calculation
The PDF’s important rule is:

if auto-add is off, the transaction should be inserted as pending
it should not affect balances until approved
This is a very important rule for avoiding budget distortion.

8. Pending vs approved recurring transactions
Rule
Pending recurring payments should behave like this:

Pending:
transaction exists
visible in a pending approvals list
balance does not change yet
Approved:
transaction becomes verified
date can be adjusted
balance updates
UI
The app should show:

pending recurring transactions
approve/reject controls
Tables
transactions.is_verified
Calculation
Only verified transactions should affect balances.

This is why the current schema uses the condition:

only transactions where is_verified = 1 count towards balances
9. Loan and EMI rules
Rule
Loan repayments are not just one simple expense. A monthly EMI often has two parts:

principal reduction
interest expense
UI
The loan payment modal should let the user enter:

total EMI amount
principal portion
interest portion
Tables
The app uses:

accounts.interest_rate
accounts.monthly_emi
transactions for the split
Calculation
The app can calculate the split using amortization logic:

interest = remaining balance × monthly interest rate
principal = EMI - interest
new balance = old balance - principal
This logic is implemented in emi.ts.

10. Credit card payment rule
Rule
A credit card payment should not be treated like a normal expense if the goal is to track debt correctly.

UI
When paying a card:

it should appear as a transfer or liability-payment flow
not as a random monthly expense
Tables
transactions.from_account_id
transactions.to_account_id
transactions.transaction_type
Calculation
The payment should reduce the liability balance and reduce the linked bank asset balance, without artificially inflating expense reports.

11. Category and budget rules
Rule
Categories should be used for:

reporting
expense analysis
budget tracking
The PDF suggests:

categories should be separated by income vs expense
budgets can be assigned to categories
the app can show progress bars
UI
The dashboard or insights view should show:

spending by category
progress against budget
Tables
categories has:
name
type
budget
group_name
Calculation
The total spent in a category is computed from transactions matching that category and date range.

12. Event/grouping rules
Rule
A transaction can belong to an event or outing group so that users can understand context.

Example:

movie night
family trip
weekend outing
UI
The transaction form should allow picking an event/group, and the app can show grouped views.

Tables
The PDF recommends an event table, but the current schema uses categories and transactions directly. The design idea is:

transactions.event_id or transaction_group_id
Calculation
The UI can calculate:

total spent per event
remaining budget for that event
13. Undo/redo and safe deletion rules
Rule
If a user accidentally deletes something, the app should allow undo for a short window rather than deleting permanently immediately.

UI
A snackbar/toast with Undo should appear after delete.

Tables
No special table is required at first; this is an in-memory stack.

Calculation
The undo system should restore the previous transaction or account state and then recalculate balances.

14. Export/import rules
Rule
The app should support:

JSON export/import for backup and restore
Excel/XLSX export for human-readable reporting
UI
The settings page should offer:

export
import
backup restore
Tables
The export logic pulls from:

accounts
transactions
categories
credit cards
widgets
loan revisions
Calculation
Excel export should be styled and formatted, while import should map rows back into the SQLite tables.

This is handled in exportExcel.ts and AppContext.tsx.

Simple summary of the full financial system
If you want to explain the PDF to someone clearly, the easiest mental model is:

Every money movement is a transaction.
Every account balance is derived from those transactions.
Assets and liabilities are tracked separately.
Opening balances are the starting point for every account.
Only verified transactions affect balances.
Loans and credit cards need special rules.
Recurring payments can be pending before approval.
Budgets and categories are for planning and analysis.
Export/import should serve both backup and human reporting.
